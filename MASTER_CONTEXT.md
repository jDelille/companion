Described as probably the **most important TypeScript type** in the platform.

```ts
import type {
  EntityRef,
  PrincipalRef,
  TenantId,
} from "@twin/domain";

export type RiskClass =
  | "R0"
  | "R1"
  | "R2"
  | "R3"
  | "R4"
  | "R5"
  | "R6";

export type ActionStatus =
  | "proposed"
  | "authorized"
  | "denied"
  | "queued"
  | "executing"
  | "verifying"
  | "succeeded"
  | "failed"
  | "escalated"
  | "rolled_back";

export interface BusinessAction {
  id: string;

  tenantId: TenantId;

  actor: PrincipalRef;
  subject?: EntityRef;

  intent: string;
  capability: string;

  arguments: Record<string, unknown>;

  risk: RiskClass;

  sop?: {
    id: string;
    version: number;
    runId: string;
  };

  status: ActionStatus;

  createdAt: string;
}
```

### 5.1 Why it matters

All of the following are first-class `BusinessAction`s:

- send WhatsApp
- refund customer
- change appointment
- click submit in legacy portal

### 5.2 Field reference

| Field | Meaning |
|---|---|
| `actor` | Principal performing/proposing the action (human, agent, service, device) |
| `subject` | Optional entity the action concerns |
| `intent` | Why the action is being taken |
| `capability` | Canonical capability name used for routing (e.g., `customer.read`, `communication.sms.send`) |
| `arguments` | Capability-specific parameters |
| `risk` | Risk class `R0`–`R6` |
| `sop` | Optional SOP linkage: id, version, runId |
| `status` | Lifecycle state (see below) |

### 5.3 Status lifecycle values

`proposed` → `authorized` / `denied` → `queued` → `executing` → `verifying` → `succeeded` / `failed`; also `escalated` and `rolled_back`.

> The source defines the allowed values but not the exact transition rules; see [Open Questions](#224-open-questions--gaps-in-the-source).

## 7. Capability Router

```ts
export class CapabilityRouter {
  constructor(
    private readonly adapters: CapabilityAdapter[],
  ) {}

  resolve(capability: string): CapabilityAdapter {
    const adapter = this.adapters.find((candidate) =>
      candidate.supports(capability),
    );

    if (!adapter) {
      throw new Error(
        `No provider for capability: ${capability}`,
      );
    }

    return adapter;
  }
}
```

### 7.1 Future evolution

Instead of merely taking the first implementation, the router can later evaluate:

- price
- latency
- tenant preference
- region
- health
- risk
- provider availability

## 8. Authority (Separate from AI)

### 8.1 Anti-pattern

Never write:

```ts
if (modelSaysAllowed) {
   execute();
}
```

### 8.2 Correct model

```ts
export interface AuthorityRequest {
  tenantId: string;
  actor: PrincipalRef;

  action: string;
  resource?: EntityRef;

  sopId?: string;

  risk: RiskClass;

  attributes?: Record<string, unknown>;
}

export interface AuthorityDecision {
  allowed: boolean;

  approvalRequired: boolean;

  policyIds: string[];

  reasonCode:
    | "allowed"
    | "approval_required"
    | "role_denied"
    | "risk_denied"
    | "scope_denied";
}
```

### 8.3 Usage

```ts
const decision =
  await authority.evaluate({
    tenantId: action.tenantId,
    actor: action.actor,
    action: action.capability,
    resource: action.subject,
    risk: action.risk,
    sopId: action.sop?.id,
  });

if (!decision.allowed) {
  return deny(action, decision);
}

if (decision.approvalRequired) {
  return queueApproval(action);
}
```

> **This is the safety boundary.** Authorization is a deterministic service evaluated outside the model, based on actor, action, resource, risk, and SOP context.

### 8.4 Decision reason codes

| `reasonCode` | Meaning |
|---|---|
| `allowed` | Action permitted |
| `approval_required` | Permitted only after human/approval step |
| `role_denied` | Actor's role lacks permission |
| `risk_denied` | Risk class not permitted |
| `scope_denied` | Outside permitted scope/resource |

## 9. Action Executor

The complete executor is "surprisingly small." Everything else becomes an adapter.

```ts
export class ActionExecutor {
  constructor(
    private authority: AuthorityService,
    private capabilities: CapabilityRouter,
    private evidence: EvidenceStore,
  ) {}

  async execute(action: BusinessAction) {
    const authority =
      await this.authority.evaluate({
        tenantId: action.tenantId,
        actor: action.actor,
        action: action.capability,
        resource: action.subject,
        risk: action.risk,
        sopId: action.sop?.id,
      });

    if (!authority.allowed) {
      return {
        ...action,
        status: "denied" as const,
      };
    }

    if (authority.approvalRequired) {
      return {
        ...action,
        status: "escalated" as const,
      };
    }

    const adapter =
      this.capabilities.resolve(action.capability);

    const result =
      await adapter.execute(action, {
        tenantId: action.tenantId,
        correlationId: action.id,
      });

    await this.evidence.record(
      action,
      result.evidence,
    );

    return {
      ...action,
      status:
        result.success
          ? ("succeeded" as const)
          : ("failed" as const),
    };
  }
}
```

### 9.1 Execution flow

```
BusinessAction
   ↓
Authority.evaluate
   ├─ not allowed        → status: denied
   ├─ approvalRequired   → status: escalated
   └─ allowed
        ↓
   CapabilityRouter.resolve(capability)
        ↓
   adapter.execute(action, context)
        ↓
   EvidenceStore.record(action, result.evidence)
        ↓
   status: succeeded | failed
```

## 10. Odoo Adapter

The existing repository (`dojo-odoo19`) already has custom addons plus `/api/v1/ai/health`, `/discover`, and `/execute` patterns, and connects n8n to those endpoints with an API key. The adapter reuses that template.

> **Don't expose Odoo's raw ORM to agents.**

```ts
export class OdooAdapter
  implements CapabilityAdapter
{
  readonly id = "odoo";

  constructor(
    private baseUrl: string,
    private apiKey: string,
  ) {}

  supports(capability: string): boolean {
    return [
      "customer.read",
      "customer.create",
      "lead.create",
      "quote.read",
      "quote.create",
      "invoice.read",
      "appointment.create",
    ].includes(capability);
  }

  async execute(
    action: BusinessAction,
  ): Promise<ExecutionResult> {

    const response = await fetch(
      `${this.baseUrl}/api/v1/twin/execute`,
      {
        method: "POST",
        headers: {
          "Content-Type": "application/json",
          "X-Api-Key": this.apiKey,
        },
        body: JSON.stringify({
          tenant_id: action.tenantId,
          capability: action.capability,
          arguments: action.arguments,
        }),
      },
    );

    const data = await response.json();

    return {
      success: response.ok,
      data,
      evidence: [{
        type: "odoo_api_receipt",
        value: action.id,
      }],
    };
  }
}
```

**Supported capabilities (initial):** `customer.read`, `customer.create`, `lead.create`, `quote.read`, `quote.create`, `invoice.read`, `appointment.create`.

**Placement:** Create a **new Odoo addon** at `odoo/addons/twin_gateway/` rather than modifying Odoo core.

## 11. Odoo `twin_gateway` Addon

```python
from odoo import http
from odoo.http import request


class TwinGateway(http.Controller):

    @http.route(
        "/api/v1/twin/execute",
        type="json",
        auth="none",
        methods=["POST"],
        csrf=False,
    )
    def execute(self, **payload):

        capability = payload.get("capability")
        args = payload.get("arguments", {})

        handlers = {
            "customer.read": self.customer_read,
            "lead.create": self.lead_create,
            "invoice.read": self.invoice_read,
        }

        handler = handlers.get(capability)

        if handler is None:
            return {
                "ok": False,
                "error": "unsupported_capability",
            }

        return handler(args)

    def customer_read(self, args):
        partner = request.env["res.partner"].sudo().browse(
            args["customer_id"]
        )

        return {
            "ok": True,
            "customer": {
                "id": partner.id,
                "name": partner.name,
            },
        }

    def lead_create(self, args):
        lead = request.env["crm.lead"].sudo().create({
            "name": args["name"],
            "phone": args.get("phone"),
            "email_from": args.get("email"),
        })

        return {
            "ok": True,
            "lead_id": lead.id,
        }
```

**Guidance:** "Then incrementally map Odoo business semantics."

### 11.1 Agent Notes on this sample

The source marks this as "roughly like this." The sample uses `auth="none"` and `.sudo()`, and `invoice_read` is referenced in the handler map but not implemented in the snippet. Before production use, add real API-key validation on the Odoo side, tenant scoping (the TS adapter sends `tenant_id`, but the sample controller doesn't use it), and the missing handlers. This is flagged here so the sketch isn't copied as-is.

## 12. SOPs as Code-Addressable YAML

Example SOP:

```yaml
id: missed_call_recovery
version: 1

trigger:
  event: communication.voice.missed

subject:
  resolver: caller_identity

states:

  identify:
    capability: customer.resolve
    next: consent

  consent:
    decision:
      options:
        - send_message
        - escalate
        - stop

  send_message:
    capability: communication.sms.send
    risk: R2
    next: wait_response

  wait_response:
    wait:
      event: communication.message.received
      timeout: 24h

  complete:
    terminal: true
```

The runtime parses this into a graph. This becomes the proprietary **Twin SOP IR** (`packages/sop-ir`).

### 12.1 SOP element reference

| Element | Meaning |
|---|---|
| `id`, `version` | SOP identity and version (referenced by `BusinessAction.sop`) |
| `trigger.event` | Canonical event type that starts a run |
| `subject.resolver` | How the subject entity is resolved (e.g., `caller_identity`) |
| `states.<name>.capability` | Capability invoked in that state |
| `states.<name>.next` | Next state |
| `states.<name>.decision.options` | Decision node with permitted option IDs (candidate for Jev) |
| `states.<name>.risk` | Risk class for the action in that state |
| `states.<name>.wait` | Wait for an event with timeout |
| `states.<name>.terminal` | Terminal state |

### 12.2 Flow of the example

```
communication.voice.missed
   ↓
identify (customer.resolve)
   ↓
consent (decision: send_message | escalate | stop)
   ↓ send_message
send_message (communication.sms.send, risk R2)
   ↓
wait_response (wait for communication.message.received, timeout 24h)
   ↓
complete
```

The `jev-skill` examples support this architecture: its `jev-act` examples repeatedly frame Jev as **choosing among permitted actions** while the **host validates and executes** them, including browser actions and outcome verification.

```ts
  situation: string;

  options: Array<{
    id: string;
    description: string;

  context: Record<string, unknown>;
```

```ts
const decision =
```

## 14. Browser Jev Adapter

`jev-ultrafast` describes itself as using a **dynamic indexed browser action space**: Jev selects the operation and element, while a small language model supplies text only for text-entry operations. It is wrapped behind the same capability interface:

```ts
export class BrowserJevAdapter
  implements CapabilityAdapter
{
  id = "browser-jev";

  supports(capability: string) {
    return capability.startsWith("browser.");
  }

  async execute(
    action: BusinessAction,
  ): Promise<ExecutionResult> {

    const session =
      await browserWorkers.spawn({
        tenantId: action.tenantId,
        isolated: true,
      });

    try {
      const result =
        await session.run({
          capability: action.capability,
          goal: action.arguments.goal,
          allowedDomains:
            action.arguments.allowedDomains,
        });

      return {
        success: result.verified,
        data: result,
        evidence: result.screenshots.map(
          (url: string) => ({
            type: "screenshot",
            value: url,
          }),
        ),
      };
    } finally {
      await session.destroy();
    }
  }
}
```

### 14.1 Key design points

- **Capability prefix:** handles any capability starting with `browser.`
- **Isolation:** each action gets a tenant-scoped, isolated browser session that is always destroyed (`finally`).
- **Domain allowlist:** `allowedDomains` constrains where the browser may go.
- **Evidence:** screenshots are returned as evidence.
- **Verification over claims:** `success: result.verified` — success is based on **verified** outcome, "not merely: agent said DONE." The Mobile-Jev project's demonstration follows the same philosophy: it re-reads the Android screen to verify the setting actually changed rather than accepting a model's completion claim.

## 18. Transactional Outbox

**Don't do this:**

| Term | Definition |
|---|---|
| **Business Twin** | A digital/operational model of a business (entities, people, agents, SOPs, devices, policies) |

| **Facility Edge / Facility Node** | Electron desktop shell running at a physical facility |
| **Conveyor** | Typed IPC layer in `electron-react-app` (query / command / stream / event) |

- Do not expose Odoo's raw ORM to agents; use the narrow `twin_gateway` capability API.
- Never import treg (or any provider SDK) directly in the core platform.
- Success for browser/mobile actions means **verified outcome**, not model self-report.
- Use a transactional outbox for event publication from the start.
- Enforce tenant scoping centrally; add PostgreSQL RLS later as a second layer.
- Do not modify Odoo core; use addons.

## 11. React 19.3 Adaptive UI Stack (`<ViewTransition>`)

### 11.1 Premise

React 19.3 changes the implementation plan because **`<ViewTransition>` is now stable**. Use it for **object continuity**.

### 11.2 Example

```tsx
import {
  startTransition,
  ViewTransition,
} from "react";

export function MemberCard({
  member,
  onOpen,
}: Props) {
  return (
    <ViewTransition
      name={`member-${member.id}`}
    >
      <article className="member-card">
        <MemberAvatar member={member} />

        <div>
          <strong>{member.name}</strong>
          <span>{member.rankLabel}</span>
        </div>

        <button
          onClick={() => {
            startTransition(() => {
              onOpen(member.id);
            });
          }}
        >
          Open
        </button>
      </article>
    </ViewTransition>
  );
}
```

### 11.3 Intended effect

```
Member card
    ↓ morph
Member leaf
    ↓ morph
Member 360
```

Visual identity is preserved across the progression. **No decorative wipe animation required.**

### 11.4 Key mechanics

| Item | Detail |
|---|---|
| `name` | Shared transition name, unique per object: `member-${member.id}` |
| Trigger | State change wrapped in `startTransition(...)` |
| Goal | Continuity of the same object across surfaces (card → leaf → 360), not decoration |

## 12. React `<Activity>` and Workspace Navigation

### 12.1 Premise

`<Activity>` is ideal for the **persistent workspace model**: hidden components **keep state** while effects are cleaned up and restored appropriately.

### 12.2 Example

```tsx
import { Activity } from "react";

export function WorkspaceStack({
  activeId,
  workspaces,
}: Props) {
  return (
    <>
      {workspaces.map((workspace) => (
        <Activity
          key={workspace.id}
          mode={
            workspace.id === activeId
              ? "visible"
              : "hidden"
          }
        >
          <Workspace
            workspace={workspace}
          />
        </Activity>
      ))}
    </>
  );
}
```

### 12.3 What it enables

A user can keep multiple workspaces open:

```
[Today]
[Maya Chen]
[September Test]
[Thursday Schedule]
```

…and return without losing:

- scroll position
- draft note
- selected tab
- filters
- expanded curriculum node
- message draft
- selected test candidate

> A material improvement over unmount/remount page navigation.

## 13. Scoped View Transitions for Local Transformations

### 13.1 Premise

Browser-level **element-scoped transitions** now let a subsection animate while the rest of the page stays interactive.

### 13.2 Use for

- calendar day change
- kanban stage movement
- testing candidate → score form
- card density changes
- table ↔ cards
- inventory count updates

### 13.3 Defensive helper

```ts
export function scopedTransition(
  root: HTMLElement,
  update: () => void,
) {
  const element =
    root as HTMLElement & {
      startViewTransition?: (
        fn: () => void
      ) => {
        finished: Promise<void>;
      };
    };

  if (
    window.matchMedia(
      "(prefers-reduced-motion: reduce)"
    ).matches ||
    !element.startViewTransition
  ) {
    update();
    return;
  }

  element.startViewTransition(update);
}
```

**Behavior:** Falls back to a plain `update()` when the user prefers reduced motion or the browser lacks `startViewTransition`.

### 13.4 Which mechanism to use

| Situation | Use |
|---|---|
| React-managed entity movement | React 19.3 `<ViewTransition>` |
| Isolated DOM/workspace primitives outside React's transition boundary | Scoped browser transitions (`scopedTransition`) |

> **Don't stack both mechanisms on the same mutation.**

## 14. Popover API Replaces Home-Grown Menus

### 14.1 Premise

The Popover API is now broadly available across current browsers and provides **top-layer rendering, light dismiss, and accessibility-related behavior**.

### 14.2 Contextual menu markup

```html
<button
  id="member-actions"
  popovertarget="member-menu"
>
  •••
</button>

<div
  id="member-menu"
  popover="auto"
  class="object-menu"
>
  <button>Check In</button>
  <button>Book</button>
  <button>Message</button>
  <button>Edit</button>
  <button>Do For Me</button>
</div>
```

### 14.3 Positioning with CSS anchor positioning

CSS anchor positioning lets the popover follow its trigger without Popper-style JavaScript calculations. **Popover invokers form an implicit anchor relationship.**

```css
.object-menu {
  margin: 0;
  inset: auto;

  position-area: block-end span-inline-end;

  width: 220px;

  border: 1px solid var(--line);
  border-radius: 14px;

  background: var(--raised);
  color: var(--text);

  box-shadow: var(--shadow-floating);
}
```

### 14.4 Which popover mode to use

| Attribute | Use for |
|---|---|
| `popover="auto"` | Menus and disposable **Peek** surfaces |
| `popover="manual"` | Persistent nonmodal surfaces where the application controls lifecycle |
| Proper `<dialog>` | Truly blocking, consequential confirmation |

## Agent Notes: Checklists, Constraints, Open Questions

> This section is derived from the writeup to help an agent plan work. It is not part of the original text.

### Implementation checklist

1. **Transitions:** Use `<ViewTransition name={...}>` + `startTransition` for card → leaf → 360 continuity; use `scopedTransition` only for non-React DOM primitives; never both on one mutation; always respect `prefers-reduced-motion`.
2. **Workspaces:** Render open workspaces inside `<Activity mode="visible"|"hidden">` so state (scroll, drafts, tabs, filters, expanded nodes, selections) survives switching.
3. **Overlays:** Build only the six overlay types (Menu, Peek, Work Leaf, Tray, Dialog, Full Workspace). Use native Popover (`auto` for menus/Peeks, `manual` for persistent nonmodal) with CSS anchor positioning; use `<dialog>` only for blocking confirmations.
4. **Object model:** Implement the universal object interface (identity, status, attributes, relationships, actions, edit, ask, do for me, timeline, history, audit) for all canonical objects.
5. **Editing:** In-place editable fields with four policy-driven render states (edit / request change / agent prepare / read only); no separate settings page for ordinary edits.
6. **Explainability:** Every unavailable action gets a "why can't I" explanation and a path forward.
7. **Kiosk:** Separate auth from staff/admin; offline attendance queue with idempotent replay; privacy auto-clear and idle timeout; safe-area aware, large targets.
8. **Role experiences:** Member / Guardian / Payer / Youth nav sets; search-first Front Desk; teaching-first Instructor Mode.

### Constraints to respect

- AI failure must **never** block kiosk check-in; kiosk has no AI requirement.
- **No billing writes offline**; **no rank changes from kiosk**.
- No public debt disclosure on kiosk; no general member editing on kiosk.
- Youth accounts: no payer/billing controls; no public leaderboard by default.
- No stacked/nested modals.
- Navigation is a fallback; prioritize search and intent.
- Instructor Mode shows no revenue, marketing, or finance content; AI supports only the five teaching questions.

### Open questions / gaps in the source

- The **`Props`** types, `MemberAvatar`, and `Workspace` components are referenced but not defined.
- **Browser support specifics** for element-scoped view transitions and anchor positioning are asserted ("now available/broadly available") but not enumerated; verify before relying on them.

## 1. Core Concept: The vNext System

### 1.1 Shift in organization

The platform is **no longer** organized conceptually by traditional modules:

- Dashboard
- CRM
- Members
- Billing
- Reports
- AI

It is **now** organized around **Intent**, executed through a shared contract/permission/service stack.

### 1.2 Architecture diagram

```
                  MARTIAL ARTS OS vNEXT

                            INTENT
                              │
              ┌───────────────┼───────────────┐
              │               │               │
            HUMAN            AGENT            SOP
              │               │               │
              └───────────────┼───────────────┘
                              │
                       ACTION CONTRACT
                              │
                     PERMISSION / POLICY
                              │
                       DOMAIN SERVICES
                              │
             ┌────────────────┼────────────────┐
             │                │                │
           ODOO           PLATFORM DB       PROVIDERS
          20 / hybrid       + events         MCP/API
```

### 1.3 Layer-by-layer explanation

| Layer | Role |
|---|---|
| **Intent** | The origin of any action. Comes from one of three sources: **Human** (staff/user in a UI), **Agent** (AI), or **SOP** (standard operating procedure automation). |
| **Action Contract** | A single, typed contract all three intent sources go through. Every experience shares the same business objects and commands. |
| **Permission / Policy** | Authorization and policy enforcement applied to every action regardless of who/what initiated it. |
| **Domain Services** | Business logic layer that sits between policy and data/provider systems. |
| **Odoo** | Operational system of record (Odoo 20 / hybrid). |
| **Platform DB + events** | The platform's own database (PostgreSQL via Prisma) plus an event stream. |
| **Providers (MCP/API)** | External providers/integrations reached via MCP or direct API. |

### 1.4 Key invariant

> Every experience shares the **same business objects and commands**.

Experiences differ in presentation and workflow, not in underlying data model or command set.

## 7. Odoo API Strategy for v20

### 7.1 Facts from Odoo documentation

- **JSON-2** is the modern external object API.
- Older **XML-RPC / JSON-RPC** services were **deprecated beginning in Odoo 19**.
- The **database service is removed in Odoo 20**.
- Remaining **common/object RPC** services are scheduled for later removal.

### 7.3 Preferred call chain

```
CUSTOM UI
   ↓
PLATFORM DOMAIN API
   ↓
OdooAdapter
   ├─ custom Odoo controller
   ├─ JSON-2 where appropriate
   └─ internal module service
```

### 7.4 Example

**Do this:**


**Not this (from React):**

```

```

### 7.5 Rationale

Hiding Odoo model details behind the platform domain API means **Odoo models can change without rewriting the front end**.

## 8. Design Principle: Capability Over Screen Size

### 8.1 The Apple Duo lesson

The most valuable Apple idea is **not** "make a foldable design." It is:

> **Design for available capability and space, not named devices.**

### 8.2 Apple's guidance (as summarized)

- Do **not** build distinct interfaces for every Duo pose.
- Use **compact vs regular** layout behavior.
- Use **safe-area-aware controls**.
- Use **split views** where space allows.
- **Reorganize existing content** rather than inventing different features.

### 8.3 Anti-pattern vs. pattern

**Avoid:**

```ts
if (isPhone) ...
if (isTablet) ...
if (isDesktop) ...
```

**Use:**

```ts
type LayoutClass =
  | "compact"
  | "standard"
  | "expanded"
  | "wide";

type InputClass =
  | "touch"
  | "pointer"
  | "mixed";

type PaneCapacity =
  | 1
  | 2
  | 3
  | 4;
```

Compose experiences around **capability**.

## 9. AdaptiveEnvironment Model

### 9.1 Interface

```ts
export interface AdaptiveEnvironment {
  layout:
    | "compact"
    | "standard"
    | "expanded"
    | "wide";

  panes: 1 | 2 | 3 | 4;

  input:
    | "touch"
    | "pointer"
    | "mixed";

  orientation:
    | "portrait"
    | "landscape";

  safeArea: {
    top: number;
    right: number;
    bottom: number;
    left: number;
  };

  reservedRegions: ReservedRegion[];

  kiosk: boolean;
}
```

### 9.2 Field reference

| Field | Meaning |
|---|---|
| `layout` | Capability-based layout class: `compact` / `standard` / `expanded` / `wide`. |
| `panes` | How many simultaneous panes the available space supports (1–4). |
| `input` | Dominant input style: `touch`, `pointer`, or `mixed`. |
| `orientation` | `portrait` or `landscape`. |
| `safeArea` | Inset pixel values (top/right/bottom/left). |
| `reservedRegions` | Areas the UI must avoid or displace around (see below). |
| `kiosk` | Whether the app is running in kiosk mode. |

### 9.3 About `reservedRegions`

> `reservedRegions` is **our abstraction**, not a claim that all browsers expose Apple's hardware APIs.

**Web inputs that feed it:**

- Container geometry
- Safe-area `env()`
- User preferences
- Application overlays
- Virtual keyboard
- PWA display mode

**Future native iPhone Duo Companion path:**

```
SwiftUI ReservedRegion
↓
native bridge
↓
same AdaptiveEnvironment
```

**Benefit:** The React UI doesn't need to care whether the reserved region is a:

- hinge
- camera
- native toolbar
- virtual keyboard
- desktop panel
- in-app call capsule

## 11. Displacement Instead of Disappearing Controls

### 11.1 Concept

Apple's Duo guidance introduces **displacement**: when a reserved area interferes, **move related objects together and preserve their spatial relationship** rather than simply hiding one.

```
              [ ✦ ]
```

Tap ✦:

```
│ suggestion         │
│ evidence           │
│ action             │
└────────────────────┘
```

### 11.3 Principle

> The Companion didn't disappear. It changed presentation.

## How each side talks to Odoo
- **v1** uses two paths:
  - **Kiosk/staff gateway:** `src/server/odoo-gateway.ts` calls `/kiosk/v2/*` with the kiosk token and the staff gateway key.
